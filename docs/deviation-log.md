- 2026-09-24 / **New pre-declared secondary analysis: parameter count without the output head** / A check of our internal reading notes found that the N of iso-depth includes neither the embedding nor the output head (its Sec. 3.2, "total non-embedding parameters"), whereas this study follows Porian / Parcae and counts the output head in N. - 2026-09-24 / **Evaluation protocol: the primary metric becomes the end-of-cooldown loss; the three-point mean is demoted to a robustness metric** / Code review found an error in the original implementation: a tail evaluation was run at the last cooldown step, and the same weights were evaluated once more at wrap-up, so "the mean of the last 3 checkpoints" was in fact (L₋₂₅ + 2·L₀)/3, while the evaluation 50 steps before the end was computed but discarded. When fixing this, a further consideration: the loss decreases monotonically during the cooldown, so averaging the last few points is systematically biased upward; the size of the bias depends on how long the cooldown is, the short runs of the small rungs are biased the most, and this would make the ruler bend slightly with scale; meanwhile the validation sets are fixed and large enough that the evaluation noise of the end-point loss is small anyway. Therefore, before any data exist, the metric is changed: the primary metric is the end-of-cooldown loss on all validation sets, consistent with the practice of Hägele et al.; the pre-registered three-point mean (50 steps before the end, 25 steps before the end, and the end) is kept as a robustness metric, computed only on the main validation set and the second validation set. Both metrics are written to the results, both are fitted, and both are reported. Side effect: the evaluation cost per branch drops from 4 full evaluations to 1 full plus 2 partial evaluations / the definition of the primary metric changes, before any data exist; both metrics will be reported, and if their conclusions disagree this will be stated openly.

- 2026-09-24 / **Implementation bug fix: truncated backprop received no gradients under bf16 mixed precision** / In the throughput test on GS01, every "middle block, r=8, truncated" setting failed with the error "checkpoint recomputed values differ from the forward pass". After reproducing this on the local machine with PyTorch 2.6.0 installed (the same as GS01), the root cause was confirmed: autocast caches bf16 copies of the weights; with truncation, the first r−k loops run under no_grad, so the cached copies have no gradient path, and the following k loops with gradients reuse them, so the looped core and the injection layer receive no gradient at all. With checkpointing enabled this shows up as a recomputation error; without checkpointing (e.g. middle block r=4 truncated) it silently trains incorrectly. PyTorch 2.14 has changed this caching behavior, which is why it did not reproduce on the local machine at first. Fix: call torch.clear_autocast_cache() after the no_grad loops. The explicit import of torch.utils.checkpoint was also added (2.6 does not load that submodule automatically). New regression test: under bf16 autocast on CPU and CUDA, for both loop placements, with and without checkpointing, and with and without truncation, the cosine similarity between the gradients and the fp32 gradients must exceed 0.98; under PyTorch 2.6, removing the fix makes 4 cases of this test fail, and with the fix all pass / found and fixed before any main-grid training; the learning-rate sweep contains no truncated cells and is not affected.

- 2026-09-24 / **Pre-declared rule for choosing the learning rates, written before any sweep result existed** / The pre-registration only says "a 5-point sweep per width at factor-2 spacing" and "a ±2× cross-check at 80M, r=4"; it does not say how to pick a value from the 5 points, nor give the criteria for the two accompanying judgments.
